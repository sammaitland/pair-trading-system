# Delisting Handler

Resolves positions when one leg of a pair is acquired or delisted: closes the
orphaned counterpart, liquidates any securities received in the deal, and records
the trade in a way that does not contaminate the calibration data set.

---

## The problem

A pair position is two offsetting legs. Its risk profile depends on both existing.
When one leg is acquired, delisted or otherwise ceases to trade, three separate
things break at once — and they are usually treated as one problem when they are
not.

**1. Risk.** The remaining leg is no longer hedged. A position that was constructed
as a market-neutral, sector-neutral relative-value trade becomes an outright
directional holding, sized as if it were still hedged. Nothing in the normal
lifecycle catches this: the exit rules evaluate the pair's combined deviation, and
that calculation depends on a price series that has stopped updating.

**2. Unexpected inventory.** In a stock-for-stock or cash-and-stock deal, shares of
the acquirer appear in the account. The system did not open that position, has no
record of it, and will not manage or close it. It sits outside the portfolio state
entirely — invisible to constraint checks, invisible to reconciliation.

**3. Record integrity.** The trade must leave the live portfolio and enter the
completed-trade history. But it did not exit for any reason the strategy generated,
and its realised return is not attributable to the strategy.

**Therefore:** delisting is not an exit condition to be added to the exit rules. It
is an out-of-band event requiring a separate procedure that touches execution,
account reconciliation and the historical record.

---

## Design decision: censor the return, keep the record

The completed-trade history is the calibration input for the exit strategy. Exit
thresholds are fitted against realised outcomes across the full trade history.
Anything written into that file propagates into future trading behaviour.

A delisting exit has a realised P&L, but that P&L is not evidence about the exit
rules. The pair was closed by a corporate action at whatever price the counterpart
happened to fill at, on a date chosen by an acquirer.

Three options:

| Option | Effect on calibration |
| --- | --- |
| Record the realised return normally | Injects a return generated by an unrelated process into the sample the exit rules are fitted to. Biases in an unknown direction. |
| Drop the trade entirely | Removes the trade from the denominator. The history then implies the strategy never held it — a survivorship-style distortion, and the trade becomes unauditable. |
| Retain the record, mark the return unavailable | Trade remains visible and countable. Return is explicitly absent rather than absent-by-omission. |

**Therefore:** the handler writes the trade to the completed history with a
dedicated exit reason and a null alpha return. Anything computing statistics over
the history can count the position and see that its outcome is undefined; anything
fitting exit rules can filter on the exit reason and exclude it deliberately.

This is censoring rather than deletion, and the distinction is the point. A missing
row and a row with a missing value carry very different information.

The exit note additionally records the acquirer, the deal terms as supplied, and
the counterpart's fill price or failure message — so that the record explains
itself years later without reference to external context.

> **Dependency this creates.** The censoring only works if downstream consumers
> filter on exit reason. Any statistic computed over the history that ignores the
> reason field will silently include a censored row. The exclusion is currently a
> convention rather than an enforced contract.
>
> **Improvement identified:** provide a single accessor for the completed-trade
> history that excludes non-strategy exits by default and requires an explicit
> argument to include them. Make the safe behaviour the default one.

## Design decision: human-invoked, not automated

Detection and handling are deliberately separate.

**Detection** is a scheduled screen. It attempts to qualify a contract for every
ticker held in the portfolio and reports failures. Qualification failure is a
*proxy* for delisting, and a noisy one — it also fires on connectivity problems,
timeouts, symbol changes and ticker reassignments. It cannot distinguish these.

**Handling** is invoked by a human, with an explicit dry-run mode that reports the
full intended action set — affected pairs, counterparts, directions, quantities —
without placing any order.

The reasoning for not automating:

- The action is **irreversible**. It closes real positions at market.
- The signal is **unreliable**. Acting automatically on a proxy this noisy means
  liquidating good positions during a connectivity incident.
- The procedure **needs information the system cannot obtain**. Deal terms, the
  exchange ratio, whether the consideration is cash or stock, and the acquirer's
  ticker are not available from the broker API at the time the position stops
  trading.
- The event is **rare**. There is no throughput argument for automation.

**Therefore:** automation is scoped to detection and simulation. The screen runs on
schedule and raises a human; the human supplies the deal context and runs the dry
run; only then does execution occur. Automating a rare, irreversible action on an
unreliable signal to save a few minutes per quarter is a poor trade.

The dry run is not a convenience feature. It is the mechanism by which the operator
verifies that the system's view of the position — which legs, which directions,
which quantities — matches reality before anything is sent.

---

## Execution approach

Counterpart closes use limit orders priced through the touch by a configured buffer,
falling back to market if bid or ask is unavailable. The order is monitored to a
timeout, partial fills are captured and recorded at the filled quantity, and
unfilled orders are cancelled rather than left resting.

The limit order gets a longer timeout than the market fallback, reflecting that a
limit through the touch is expected to fill but not instantly, whereas a market
order that has not filled within a short window indicates a problem rather than
patience.

**Therefore:** the default path prices deliberately rather than crossing the spread
blind, but the failure mode is a cancelled order and a reported failure — never a
partially-managed position with no record of what happened.

## Known defect: partial-failure handling

**This module has a bug in its failure path. It is documented here rather than
hidden because the failure mode is instructive.**

The handler closes counterparts in a loop, collecting per-close results. It then
records all affected trades to the completed history and removes all affected
trades from the portfolio — using the set of affected trades, not the set of
*successfully closed* ones.

The overall success flag is computed correctly and reports the partial failure. But
the state mutations have already happened unconditionally.

**Consequence:** if a counterpart close fails — unfilled, cancelled, contract
unqualifiable — the position remains live in the account, but it has been removed
from the portfolio file and written to the completed history. The system now
believes it holds nothing while holding an unhedged directional position. It is
outside constraint checks, outside stop-loss protection, and outside the exit
lifecycle. It will only resurface through account reconciliation.

This is the same failure class the module exists to prevent: an untracked,
unhedged position. The handler can create one while resolving one.

**Correct behaviour:** record and remove per trade, conditional on that trade's
counterpart close succeeding. Failed closes remain in the portfolio, retain their
tracking, and are reported for retry. The operation should be idempotent — re-running
after a partial failure should resolve only the outstanding trades.

**Related, lower severity:**

- The completed-trade history is written by full-file overwrite with no backup and
  no atomic rename. An interruption mid-write, or an unexpected sheet in the source
  workbook, loses the canonical trade record. The portfolio file save is
  sheet-aware; the history save is not. The asymmetry is unintentional.
- Option positions are read from the portfolio workbook and written back unchanged.
  Whether an option hedge associated with a delisted pair is orphaned by this
  procedure is currently unresolved.

## Interface

```
handle_delisting(ticker, acquirer=None, deal_notes=None,
                 liquidate_acquirer=False, dry_run=False) -> dict
```

```
check_for_delistings() -> DataFrame
```

**Detection reads** the live portfolio and the broker's contract database.
**Detection returns** tickers that failed qualification, with the pairs affected.
It asserts nothing about the cause.

**Handler reads** the live portfolio, live account positions, deal context supplied
by the operator.
**Handler writes** closing orders for counterpart legs, an optional liquidating
order for received securities, censored records in the completed history, an
updated portfolio state.
**Handler returns** a per-step result structure including individual close outcomes.

**Guarantees**
- `dry_run=True` places no orders and mutates no files
- the broker connection is released on every exit path, including exceptions
- a pair not present in the portfolio is a no-op, not an error

**Does not**
- detect delistings on its own — detection is a separate, scheduled function
- determine deal terms; these are operator-supplied
- guarantee consistency between account state and portfolio state on partial
  failure (see defect above)
